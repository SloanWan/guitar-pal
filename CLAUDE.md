## Architecture

**Auth flow:** `/auth` handles sign-in/sign-up via `src/lib/auth.ts`. `src/proxy.ts` is the Next.js 16 middleware entry point (named `proxy.ts`, not `middleware.ts`) and its matcher runs on nearly every request, not a route list — it refreshes the session cookie on each one, so a redirect has to carry those cookies across (`redirectWithCookies`) or the refresh is dropped. A request that cannot reach Supabase is treated as signed out rather than thrown, so the public pages still render.

- `/home` and `/settings` are the signed-in personal surfaces, matched **exactly**, not as prefixes. A signed-out visitor goes to `/auth?redirect=…` and lands back after signing in.
- `/` is the public hub. A signed-in visitor is sent to `/home`; a signed-out one stays, deliberately (#127).
- `/auth` sends a signed-in visitor to the `redirect` param when `safeRedirectPath` accepts it, else to `/home`.
- `/books` is open to everyone (#262) — uploading asks for an account on the page, not at the door.
- `/dev` with `NEXT_PUBLIC_ENABLE_DEV_ROUTES` unset returns unchanged so the dev layout can 404 it; redirecting there would leak that the route exists. With the flag on, every `/dev` page is open.

Everything else is public.

**Two Supabase clients:**

- `src/lib/supabase.ts` — `createClient()` via `createBrowserClient`, used in client components and all lib query functions
- `src/lib/supabase-server.ts` — `createSupabaseServer()` via `createServerClient` + `cookies()`, used only in server components and route handlers (`(main)/p/[id]/page.tsx`, `api/assistant/route.ts`, `api/books/[...path]/route.ts`). Note the chord pages are **not** on this path: they read through `chordsData.ts`, which uses a cookie-free `@supabase/supabase-js` client so `unstable_cache` can wrap the reads

Never mix the two clients — `createSupabaseServer()` throws at runtime in client components.

Env vars required: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`.

**Data layer:** `src/lib/` contains thin Supabase query functions — no ORM, no server actions (except the two chord reads client components make, in `chords.ts`). All DB calls happen client-side. Lib functions throw on Supabase error rather than returning null. The full structure (columns, indexes, RLS policies, grants) is `scripts/schema.sql`; the main tables:

- `exercises`, `routines`, `routine_exercises`, `practice_logs`, `exercise_logs` — the practice-routine tables; nothing reads them since the dev dashboard and session pages were removed (#363 cleanup)
- `user_strum_patterns`, `user_favourite_patterns` — custom strum pattern storage
- `user_favourite_chords` — the chords a player keeps, by `root` + `suffix` (never a voicing); signed out they live in localStorage and join the account on the first signed-in load (`useFavouriteChords`). The pick toggle is the shared `ui/pick-toggle.tsx`, also the Strum library's
- `user_pattern_progressions` — chord sequences a user attached to a strum pattern (`pattern_id` is a plain text id, not a foreign key: a progression can hang off a preset pattern as well as a custom one)
- `user_visits` — how often a player opened each strum pattern, tab, chord and book (`kind` + `target`, a count and `last_at`), for Home's "Most opened" (#399). Only ever incremented through the `record_visit` RPC (an upsert of `count + 1`); `recordVisit` / `useRecordVisit` count a thing once per browser-tab session and record nothing signed out or on a share
- `chords`, `chord_voicings` — shared/read-only reference data

Types defined in `src/types/database.ts`.

**Strumming machine audio engine** (`src/components/strum/`):

- `useAudioEngine.ts` — setTimeout-based lookahead scheduler (100 ms window, 25 ms reschedule). All scheduler-read state lives in `useRef`, never `useState`, to avoid stale closures and re-render-triggered timing drift. Do not read `ref.current` values inside React render logic.
- `useGuitarSampleLoader.ts` — reads the bundled presets: `fetchPreset(key)` gets `PRESET_BASE_URL` + key + `.json` from our own origin and `parsePreset` checks every zone; `pianoSampleLoader.ts` uses the same pair. **Nothing downloaded is evaluated** (#366): the CDN's files are JavaScript, so `scripts/convert-webaudiofont-presets.mjs` converted them to JSON once, offline, against pinned SHA-256s. To add a preset, add it to that script and re-run it; never fetch the CDN at runtime. Only the `/dev` audition pages, which browse the whole CDN, still parse its JS (`src/app/dev/_lib/parsePresetFromJs.ts`, `new Function()`; a hand-rolled tokenizer was tried there and broke on real CDN content) — keep that module out of anything outside `src/app/dev`. Exposes `triggerStrum(type, ctx, target, when, noteDuration, customPitches?)`, which directly schedules one `AudioBufferSourceNode` per string (5 strings, 10 ms stagger, 0.9× volume taper) using the Web Audio API. `customPitches` carries the sounding bar's chord (resolved by `resolveBarChords`); without it the default C-major voicing (MIDI [48, 52, 55, 60, 64]) plays. The `WebAudioFontPlayer` class is not used. Down strum: low→high pitch order; up strum: high→low. Exposes `preloadStrumPresets(ctx)` (call once on playback start) and `cancelStrums()` (call on stop and unmount).
- Struck strings **let ring**: down/up strums decay over `STRUM_RING_SECONDS` (1.5 s, τ = ring/3) regardless of tempo, so consecutive strums overlap the way a real guitar does. `noteDuration` (= `secondsPerCell`) now only bounds the muted chuck, which stays capped at `MUTED_MAX_DURATION_S` and keeps the BPM-scaled decay. Play-once therefore waits a full ring before `cancelStrums()`, or it clips its own closing chord. Settings were chosen in `/dev/strum-sound-lab`.

**Strum pattern model** (`src/lib/strumPatterns.ts`, `strumBars.ts`, `strumRhythm.ts`, `strumNotation.ts`, `strumProgressions.ts`, `strumGridLayout.ts`):

- A `StrumPattern` is **the rhythm** — `{ id, name, beats, extraBars?, bpm?, meter? }`: one bar (`beats`), or a few that play in turn (`extraBars` holds the bars after the first). It carries no chord and no stored description: the description is written from `beats` by `patternNotation` (one character per cell, blanks where nothing is struck, so `whitespace-pre` + a mono font are required wherever it is rendered). Stored, `user_strum_patterns.bars` holds the whole rhythm chordless and `beats` its first bar (double-written); `patternFromRow` only trusts `bars` when it still reads that way, so a row left from the old chord-carrying model stays one bar.
- A `ChordProgression` is a chord sequence over a pattern: `Bar[]` (one `ChordRef` per bar), plus an optional name, tempo and capo, stored per user in `user_pattern_progressions`. **A progression always plays its pattern's rhythm**: `progressionPlayback(patternRhythm(p), progression)` lays chord `i mod chords` over rhythm bar `i mod rhythm` for `max(chords, rhythm)` bars. Each bar still stores `beats`, written from the pattern on save (`alignToRhythm`), so `Bar[]` readers (shares, the assistant) see what plays — but playback reads the pattern. Sequences written while they could drift were lifted onto patterns of their own (`liftDivergedProgressions`: `scripts/lift-diverged-progressions.ts` for accounts, `migrateGuestStrumStorage` once for a guest's browser). Unnamed progressions are listed by their chord abbreviations (`"C|G|Am|F"`). New ones are typed as a chord line (`parseChordSequence` resolves each word through the same ranked search the chord picker uses).
- `patternRhythm(pattern)` / `toBars(pattern)` (`strumRhythm.ts`) are the single read path; `withRhythm` writes one back; `rhythmOfBars` is the inverse (the shortest rhythm a run of bars repeats — how a proposal becomes a pattern); `resolveBarChords` is the `ChordRef` → MIDI boundary.
- On screen a one- or two-cell beat pads out to four columns (`paddedBeatCells` in `strumGridLayout.ts`), so a quarter, an eighth and a sixteenth beat take the same width; triplets keep their three.
- Deleting a pattern must cascade: its progressions and its favourite record go with it.

**Fingerpicking feature** (`src/lib/fingerpickTypes.ts`, `src/lib/fingerpickToVexFlow.ts`, `src/components/fingerpick/`):

- Data model in `fingerpickTypes.ts`: `FingerpickPattern` → `Measure[]` → `BeatSlot[]`. Each `BeatSlot` holds 6 `StringFret` entries (`fret`, `muted`, and the technique model v2 fields below) and a `Duration`; a slot may carry a `stroke` (sweep) or a `percussion` hit, never both.
- **Technique model v2** (`schemaVersion: 2`; `src/lib/techniqueRegistry.ts` is the one list of kinds): a note carries a `link` (how it is reached: tie, hammer, pull, slide — one per note) and an `effects` map keyed by kind (bend `{semitones, pre?, release?, hold?}`, vibrato, harmonic, tap, trill, tremolo, pick, accent, staccato, ghost, slideIn, slideOut, whammy, scrape). Runs shared by several notes are pattern-level `spans` (`palmMute`, `letRing`, `slur`) anchored on `BeatSlot.id`s (`from`/`to`, optional `strings`), so they cross barlines and survive edits elsewhere; `indexPattern` / `spanCovers` (`fingerpickIndex.ts`) are the only way to ask what a span covers, and every structural edit ends in `reconcileSpans`. **An x on a string (`muted: true`) is a slap on that string, not a silent dead note**: it sounds with the slot's other notes, and the ASCII reader takes every `x` as written. A hit (`slap`, `thumbSlap`, `bodyTap`) is a slot's `percussion`, the whole-hand shortcut over the strings nothing else strikes. The registry's `render` / `audio` flags are tested against `RENDER_KINDS` (converter) and `AUDIO_KINDS` (scheduler): adding a technique is one registry entry plus a handler in each table; the editor menu, the validator, the MCP / assistant tool schemas (`tabImport/noteInput.ts`) and the ASCII reader/writer all derive from the registry. Data written before v2 (one `technique` string, `tied`, `bendTarget`, per-note `palmMute` / `letRing` flags) is brought up by `migratePattern` on every read path (validator, `normalizeLoadedPattern`); an import draft may still flag `palmMute` / `letRing` per note (a model has no slot ids) and the migrator folds them into spans. `user_fingerpick_patterns.spans` is its own column (`scripts/add-spans-to-user-fingerpick-patterns.sql`). `TabStaveRow` / `layoutMeasureRows` take a `renderContext` (`{ index }`) so brackets crossing a barline and lead-in arcs into a row's first note are drawn; without one a measure is read on its own.
- `fingerpickToVexFlow.ts` converts a `Measure` into VexFlow `TabNote`, `GhostNote`, `TabTie`, `TabSlide`, and `Beam` objects for stave rendering.
- `TabStaveRow.tsx` renders a row of tab staves using those VexFlow objects.
- **Meter model is shared with strum** (`src/lib/strumMeter.ts`): a compound meter (6/8, 12/8) is counted in dotted-quarter beats, never in eighths. `beatTicks(ts)` in `fingerpickEdit.ts` is the only way to get "the beat" (24 or 36 ticks of 96 per whole note); nothing reads the denominator directly. **BPM counts the beat** (♩ = 90 in 4/4, ♩. = 60 in 6/8) — `secondsPerQuarter(bpm, ts)` in `fingerpickScheduler.ts` is the one place the meter enters timing, and `changeTimeSignature` rescales the tempo across simple ↔ compound so the eighth note keeps its speed.
- **Pitch is one formula** (`src/lib/fingerpickPitch.ts`): `soundingMidi(string, fret, capo)` is what the scheduler compiles events through and what the reading page's Pitch column (`TabStaveRow`'s `pitchLabel` prop, raw SVG `<text>` under the stems, footroom computed like the chord line's headroom) writes under each fret, so label and audio cannot disagree. `pitchLabel(midi, style)` spells names by `ROOT_CHROMATIC_ORDER` (styles: name, scientific, fixed-do solfège, jianpu); the `jianpu` style is fixed-do in C with the undotted octave at sounding C3–B3 (guitar is written an octave up), octave dots carried as combining marks that `splitPitchLabel` strips for drawing. The column's labels widen a measure's minimum width (`pitchLabelWidths` in `computeMeasureMinWidth`); the toggle and style are device-local prefs.
- The chord line's shape view can write each chord's tones beside its strip (`chordToneNames` in `fingerpickChords.ts`: `chordTones` by interval, the voicing's notes as fallback), sized with the strip by `chordToneFontSize`; `chordShapeSize.width` in the workspace grows by the widest tone line so lanes and the row edge are laid out for the whole overlay.
- **Bend and vibrato are one detune curve per note** (`src/lib/fingerpickExpression.ts`): `expressionForEffects(effects)` → `composeExpression(spec, duration)` gives a `Float32Array` of cents over the note's whole audible life (a vibrato rides a bend's peak when the note has both), and `scheduleFingerpickNote` sets it once with `detune.setValueCurveAtTime` on the note's own source. `playbackRate` stays the slide's (the two multiply), so a bent voice can still be slid from; a shift slide (`link.picked`) re-plucks instead. Timing is in ms, never BPM-scaled; defaults were chosen by ear in `/dev/bend-lab` and a released bend keeps τ long enough to be heard coming down (`releaseDecayTc`). The scheduler's gain ladder is a table by kind (`noteGain`); a palm-muted note is quieter, low-passed and capped at `palmMuteDecayTc`, and never rings on; a slap (an x, or a hit's strike) is three layers (`SlapParams` / `DEFAULT_SLAP_PARAMS`, tuned on `/dev/slap-lab`): the string's OWN sample at the slap gain cut off at `strikeS`, never registered as a voice — the way TuxGuitar / alphaTab (30 ticks ≈ 31 ms) and MuseScore (50 ms) play a dead note — plus one `slapNoise` event a slot (`scheduleSlapNoise`: the clack of the strings on the frets, a bandpassed noise burst, and the thud of the body, lowpassed noise with a dropping sine, mostly on the bass strings); there is no muted-guitar preset (the fingerpick loader has one sample set, `pluck`). The rest of the registry is voiced the same way: tremolo and trill are repeated strokes made in the event pass (`tremoloStrokes` / `trillStrokes`, a trill's strokes carrying hammer / pull links so the legato treatment falls out), a harmonic is the pluck sample at its partial (`harmonicShift`: a natural harmonic is the OPEN string's partial — fret 12 an octave up, 7 a twelfth, 5 two octaves — an artificial or pinch one the fretted note plus its interval; the same shift the pitch column labels) with a quiet octave under it and no filter, the way TuxGuitar and alphaTab play one, a tap starts past the sample's pick transient (`TAP_SKIP_S`) and eases in, slide-in / slide-out ramp `playbackRate` on the note's own voice, a whammy is its own curve (`whammyCurve`: a whole tone by default, reached over three quarters of the note and held, or back by the note's end when released — the TuxGuitar / Guitar Pro presets; summed with a finger bend), a slurred note (`slurredInside`) plays like a hammer-on, and a pick scrape or body tap is noise (`noiseBufferFor`, `scheduleNoiseEvent`) that registers no voice. Every kind is auditioned on `/dev/technique-gallery`. In the editor, availability comes from the registry's `available(ctx)` rules (`techniqueBlock`); `B` / `V` cycle bend and vibrato, `H` / `P` / `/` toggle a link, `M` / `L` extend a palm-mute / let-ring span, `S` slaps the slot.
- **Triplets are groups**: `tripletGroups(slots)` (three consecutive same-value triplet slots, chunked from the run start) is the single grouping the grid bracket, the VexFlow `Tuplet` and every structural edit read — deleting, duplicating or inserting around a member acts on the whole group. Triplet entry points are hidden when `isCompound(ts)`.

## Conventions

- Ghost strokes (`"DG"`/`"UG"`) are **drawn, not stored**: `ghostedBeats` in `strumGridLayout.ts` derives them from the struck cells where the grid is rendered. A stored `StepValue` is only `"D" | "U" | "X" | ""`; the retired `DG`/`UG`/`D3`/`U3` values are folded away by `normalizeBeats` (`strumBars.ts`) as rows are read. Never write a ghost into stored beats, a parser result, or an audio engine structure.
- **Candy tokens (redesign, epic #349):** `src/app/tokens.css` holds the new system as `--gp-*` custom properties (Snow neutral ramp, the matte gauge module ramps, shape, motion, type), light on `:root` and dark in both a `prefers-color-scheme` block and `[data-theme="dark"]` — keep the two dark blocks identical (`src/app/__tests__/tokens.test.ts` checks keys and contrast). `<main data-m>` (`ModuleMain`, `moduleForPath`) re-points the `--gp-m-*` aliases to the route's module (`strum`, `tab`, `chords`, `fb`, `books`, else `home`). In a mixed list (a `ListRow` given its own `module`, e.g. Home) the badge rests quiet — a neutral pick, the icon in the module's 700 — and fills only on the row pointed at or chosen (`.gp-badge-quiet`); a kept favourite there is ink. Filled pressables (primary, ink, danger) and every pick shape wear a matte grain: HTML fills overlay the `--gp-grain` tile, SVG pick paths take `filter: url(#gp-grain)` from `GrainDefs` (`ui/grain.tsx`, mounted once in the root layout) — never on a white face. Selected text is the module's Fill (`::selection` in `globals.css`: module 500 behind `--gp-m-on`, inverted on a `gp-tone-primary` fill). Utilities take the bare names (`bg-page`, `text-ink-3`, `bg-m-500`, `rounded-lg`, `ease-spring`, `font-display`) while the custom properties keep `--gp-`; `rounded-xs`…`xl` and `ease-in` / `ease-out` are Candy's values, not Tailwind's defaults. Type is Figtree (`--gp-f-body` / `-disp` / `-num`); JetBrains Mono (`--gp-f-mono`, the `font-mono` utility) is only for the tab stave's digits and typed text.
- **Candy primitives (#353):** `ui/button.tsx` (`Button` primary / secondary / ink / danger / ghost / icon, `PlayPick`), `ui/chip.tsx`, `ui/segmented.tsx`, `ui/switch.tsx`, `ui/stepper.tsx`, styled by `src/app/primitives.css` (`gp-btn`, `gp-press`, `gp-tone-*`, in `@layer components`). Every pressable takes `usePress` (`ui/press.ts`), which sets `.is-down` for pointer and Enter / Space and holds it ≥ 90ms — never hand-roll a press or a shadow on a page. Stepper logic (clamp, step, tap tempo) is `src/lib/stepper.ts`. Primitives II (#355): `ui/card.tsx` (`Card` is static content with no box; `NavCard` hops — `@property --gp-lift`, `usePress(ref, { hop: true })` hops it under a finger), `ui/list-row.tsx` (`ListRow`, `ModuleBadge`; `module` colours a row in a mixed list), `ui/panel.tsx`, `ui/input.tsx` (`Input`, `SearchInput`, `Field`), `ui/slider.tsx` (Radix; snapping in `src/lib/snap.ts`), `ui/sheet.tsx` (Radix Dialog: bottom below 720px, right panel above), `ui/skeleton.tsx` (shown after 300ms) and the restyled `ui/sonner.tsx`. A title that leans italic on hover is a `gp-title` element; Lift is `aria-current` / `aria-pressed`. All of it is on `/dev/primitives`.
- **Every page bubbles in:** put `gp-rise` (`primitives.css`) on the element holding the page's sections; its children rise 45ms apart in order (set `--i` on a child to group it with another). Never copy the keyframes into a page's stylesheet.
- **Things don't jump (spec v1.2):** a card, panel, sheet or popover keeps its size when controls inside it appear, disappear or change state. Reserve the space — disable rather than remove (the tempo panel's "Open at … from now on" is always there, disabled until the tempo differs), give changing values a fixed width with tabular numerals, keep rows a fixed height. A container changes size only when its content genuinely grows.
- **Keep related things together (spec v1.2):** controls that mean similar things or depend on each other sit side by side, in the order the task uses them — a sound's mute, what shapes it and its level on one row (the click's subdivision with the click volume), a switch next to the setting it unlocks (loop with the gap between passes), a value's quick steps on the value's own row (−10 / +10 / Tap beside the BPM).
- The `/dev` pages were never migrated (#363): their v3 class names mostly no longer resolve (a few, such as `text-ink`, now pick up the Candy value), so they render plain, and their `Fader` / `Rocker` live in `src/app/dev/_components`. Never import from there outside `src/app/dev`.
- **All code, comments, and commit messages must be in English** — no Chinese identifiers, comments, or commit messages, regardless of what language the requirement was discussed in.
- **Animation: CSS first, framer-motion for state-driven only** — pure hover/visual interactions use plain CSS `:hover` + `transition`, not `framer-motion`. Reserve `framer-motion` for animations that must be orchestrated by React state or data changes (list enter/exit, value-driven transitions). Reaching for a JS animation library for static hover effects is over-engineering.

## Development Principles

- **Issue-driven:** confirm a GitHub issue exists before writing code for a new feature. Ask if one doesn't appear to exist.
- **Small PRs:** resolve one issue at a time, broken into the smallest deployable chunks.
- **Don't over-engineer:** don't extract components or abstractions with no current reuse value.
- **Don't commit on behalf of me:**: do not commit changes until i specify so
- **Schema snapshot** (#264): `scripts/schema.sql` is the written record of the database structure. After any schema change — a table, column, index, policy or grant, whether from `scripts/*.sql`, an Alembic revision or the Supabase dashboard — run `npm run db:schema` (`scripts/dump-schema.mjs`, pg_dump of the `public` schema; reads `SCHEMA_DATABASE_URL` or `BOOK_SERVICE_MIGRATION_DATABASE_URL`) and commit the snapshot in the same PR. `schemaBaseline.test.ts` fails when the code queries, or a migration creates, a table the snapshot lacks; it cannot see a new column or policy, so for those the rule is the only guard.
- **One-time migration scripts** live in `/scripts` (`schema.sql` and `dump-schema.mjs` are not one-time), excluded from `tsconfig.json`'s type-check scope. Before writing to the database, calibrate the transform logic against a small set of known ground-truth rows already in the database — abort if calibration fails. Safe to delete after a successful run; not covered by the "core logic needs unit tests" constraint.
- **Verify third-party field semantics before writing adapters** — when integrating an external dataset or API, pull a small sample of real rows (at least one simple case and one edge case) and reverse-verify each field's meaning against known-correct values before writing any transform code. Semantics guessed wrong produce silent bugs rather than compile/runtime errors, making them more expensive to catch later.

## Constraints (apply to every task unless explicitly told otherwise)

1. Don't modify Audio Core logic (scheduler loop, ref-based state, metronome logic in `useAudioEngine.ts`) unless the task is explicitly scoped to it.
2. TypeScript strict mode; `any` is forbidden; all exported functions need complete Type/Interface definitions.
3. Core computation/data-processing logic ships with unit tests.
4. Check for memory leak risks — uncleared EventListeners, Timers, or (for audio) dangling `AudioBufferSourceNode`/scheduled-callback references.
